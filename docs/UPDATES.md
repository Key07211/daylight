# Updates

**English** · [简体中文](UPDATES.zh-CN.md)

The installed Windows app checks GitHub Releases after startup and every six hours while it is running. Checks download version information only. The installer is downloaded after you choose **Download & restart immediately**.

## Use an update

1. A blue dot appears to the right of **Pin** when a newer stable version is available. Open it to see the version and release notes.
2. Choose **Download & restart immediately**. A progress ring shows the download. Finish or save any task you are editing before starting.
3. After downloading and verifying the installer, Daylight installs the update and restarts immediately. There is no countdown or second confirmation. If an editor or a running Codex task is still active, the app waits for that work to finish, then continues automatically.

Settings also offers **Check for updates**. When the app is current, the blue dot is hidden. A failed check or download does not replace the running app; use the retry action or check again later. Tasks remain in `%APPDATA%\Daylight\data\store.json`.

Install a version with the updater manually once: versions before **0.4.0** cannot update themselves. Download the Setup installer from the [official releases](https://github.com/Key07211/daylight/releases/latest), exit Daylight, and install it. The portable edition opens the release page for a manual download; it does not install an update over itself. Source, preview, and test sessions do not run the installed-app updater.

## Release a new version

The release workflow is [`.github/workflows/release.yml`](../.github/workflows/release.yml). It runs only for pushed `v*` tags in `Key07211/daylight`. A normal code push or local build does not publish an update.

1. Choose a new stable version greater than the last public version. Update `package.json` and `package-lock.json` together, update the relevant release documentation, and commit the changes.
2. Push that commit and an exact matching tag, for example `v0.4.1` for package version `0.4.1`.
3. The Windows job installs locked dependencies, runs tests, builds both desktop editions, checks packaged startup and the installer payload, and validates update metadata.
4. It uploads the complete asset set to a draft, compares every uploaded asset's size and SHA-256 digest, and publishes only when all checks pass. A failure before publication leaves the release unavailable to the updater. Retry the workflow to resume a draft from the same commit. An existing public release is never overwritten.

Required update assets are generated by electron-builder and must stay together:

| File | Purpose |
| --- | --- |
| `latest.yml` | Version, installer filename, size, and SHA-512 |
| `Daylight-Setup-<version>.exe` | NSIS update installer |
| `Daylight-Setup-<version>.exe.blockmap` | Differential download data |

The workflow also publishes the portable executable and ZIP, bilingual offline demo ZIP, SHA-256 list, and validation report. It uses the workflow's temporary `GITHUB_TOKEN` only when publishing; no GitHub token is shipped in the app. Build settings generate an internal `resources/app-update.yml` pointing to the public repository. The updater checks stable releases and does not downgrade.

For a local build and metadata check:

```powershell
npm ci
npm test
npm run package:win -- --publish never
node scripts/verify-update-release.mjs
.\node_modules\.bin\electron.cmd desktop/update-download-smoke.cjs
```

`verify-update-release.mjs` rejects mismatched versions, unsafe or incorrect filenames, wrong sizes or SHA-512 hashes, missing/incomplete blockmaps, and a packaged update feed pointing to another repository. The download smoke uses the real Electron updater and a loopback server to download the built installer into an isolated cache. It verifies that checking does not download, a requested download reports progress, a valid download immediately requests installation/restart, and a corrupt checksum prevents installation. A spy intercepts installation, so no installer runs and the real application stays untouched. Differential downloads and actual installation/relaunch still need an isolated Windows test account or VM with an older update-capable installation and a newer release; record those results separately.

## Signing and recovery

Daylight's current Windows executables are **unsigned**. HTTPS and checksum verification protect download integrity, but are not a verified publisher identity. Windows may display an unknown-publisher or SmartScreen prompt. The application does not disable Windows protections.

Before moving to signed releases, configure Windows code signing in the build, protect the certificate or signing service credentials in GitHub, and validate the publisher name in the packaged updater configuration. Test the transition from an unsigned installation to a signed version and between signed versions. Do not describe existing unsigned releases as publisher-verified.

If an update fails, keep using the current version and retry. You can also exit Daylight and run the latest official installer manually; task data stays outside the installation directory. If a published version needs a fix, publish a higher version instead of replacing its installer or editing its checksums.

Implementation references: [electron-builder auto updates](https://www.electron.build/v26/docs/features/auto-update/) and [GitHub release creation](https://cli.github.com/manual/gh_release_create).
